# 富文本与 Markdown 双视图的无损验收标准

关联 [Issue #469](https://github.com/tianma-if/edgeever/issues/469)。本标准适用于 Web 和桌面端普通笔记的 TipTap 富文本视图、CodeMirror Markdown 源码视图，以及两者共用的保存链路。它约束的是用户笔记的可观察结果，不要求两个视图使用同一个编辑器组件。

## “无损”的三个层次

| 层次 | 判定依据 | 适用情形 |
|---|---|---|
| 源码原样保留 | Markdown 字符串严格相等，包括空行、空格、转义、实体和换行符 | 源码未被用户改动，或用户从源码视图保存后重新打开且期间未修改富文本 |
| 富文本结构保留 | 持久化的 TipTap 文档结构及用户可见属性相等 | 仅切换视图，或修改源码中与富文本专有结构无关的部分 |
| 编辑语义保留 | 文本、格式、链接目标、列表层级和勾选状态、表格数据、附件及其他受支持节点的含义相等 | 用户确实修改了富文本，允许 Markdown 序列化改变写法 |

不能把这三个层次混称为“Markdown 往返完全无损”。富文本修改后，Markdown 的空行、列表标记、转义等写法可能被重新序列化；这种情况下保证的是受支持内容的编辑语义，不保证源码逐字不变。Markdown 无法表达的富文本属性，也不能仅凭序列化后的 Markdown 判定是否丢失。

## 必须通过的场景

| 场景 | 验收断言 |
|---|---|
| A. 只切换视图 | 富文本 → Markdown → 富文本 → Markdown，不输入、不粘贴：第二次看到的源码与第一次逐字相同；富文本文档与切换前相同；切换本身不产生内容修改、保存或新修订。已有笔记使用其保存的源码，不因进入视图就重新格式化。 |
| B. 在源码视图编辑 | 保存、重新打开、再次进入源码视图后，得到用户提交的源码原文。切到富文本再切回且未改富文本时，仍得到该原文。富文本中显示的受支持内容须与该源码的解析结果一致。自动保存回填不能覆盖仍在输入的源码或移动插入点。 |
| C. 在富文本视图编辑 | 保存、重新打开后，富文本内容及其用户可见属性保持一致；生成的 Markdown 再解析后，受支持的内容语义保持一致。允许 Markdown 写法规范化，但不能把普通 `[`、`]`、`&` 显示成无必要的 `\[`、`\]`、`&amp;`；若去掉转义会改变解析结果，则必须保留转义。 |
| D. 富文本专有结构 | 仅查看源码时，富文本专有结构及属性必须原样保留。修改源码的其他位置时，未涉及的专有结构必须保留。若修改会迫使受影响结构降级，界面须在覆盖前明确说明会失去什么，并允许取消；未经告知的结构丢失为失败。 |
| E. 光标与焦点 | 在普通可编辑文本中切换，光标或选区应落在同一段可见内容的对应位置，焦点进入目标编辑器，下一次输入不得插到相邻字符之前或之后。对于 Markdown 标记、链接地址等富文本中没有对应编辑位置的区域，允许落到相邻的安全位置；不得修改内容。 |
| F. 冲突与恢复 | 自动保存、离线草稿恢复、远端修订冲突处理后，继续遵守 A–D。不同笔记的快照不得串用；冲突不得静默用旧视图覆盖新正文。 |

任何测试中正文、附件引用或不可由 Markdown 表达的结构发生静默删除，均为阻断问题，不能以“Markdown 语法等价”豁免。若能力边界无法满足 D，应保留原始数据并阻止有损覆盖，直到用户明确选择转换。

## 验收样本和执行方式

每类样本都执行 A–C；含专有结构的样本还执行 D。断言同时读取视图内容、保存前后的 `contentJson` 与 `contentMarkdown`，避免只凭截图或序列化字符串判断。

| 样本 | 必测内容 |
|---|---|
| 普通文字 | `Alpha [ ] & Bravo`、字面量 `&amp;`、可形成链接的方括号、反斜杠、美元符号、空格与连续空行、CRLF、中文和 emoji |
| Markdown 结构 | 标题、强调、链接及地址、行内与围栏代码、引用、嵌套列表、待办状态、GFM 表格、Mermaid、公式、`details` |
| EdgeEver 内容 | 图片与图集、文件和 PDF 附件、插件嵌入、合并分隔符、富文本表格单元格中的待办列表或多段落、富文本专有属性 |
| 输入与切换 | 中英文输入法组合输入、粘贴、撤销/重做、光标在标点和格式边界、选区、快速反复切换、长笔记 |

自动化至少覆盖转换与快照断言、保存后重开，以及浏览器中的实际键入和光标位置。Issue #469 的复现环境为 Windows 10 / Chrome 154 / zh-TW；关闭该问题前应在该环境或可说明差异的等效 Windows Chrome 环境复验。若修改存储格式、迁移或跨版本读取机制，还必须用真实旧版本笔记完成旧版 → 新版验证。每项记录“通过 / 失败 / 未验证”、运行平台与版本；未验证不得写成通过。

## 当前实现与未完成项（2026-10-04）

- 当前保存链路同时存储 `contentJson` 和 `contentMarkdown`。源码视图保存时发送用户原文；富文本视图保存时服务端从 JSON 生成 Markdown。因此 C 不承诺富文本编辑后的源码逐字相同。
- 现有单元测试覆盖普通 `[`、`]`、`&` 的可读源码、危险转义保留、未编辑源码的快照恢复、未编辑的复杂表格单元格以及部分光标映射；本地浏览器验证了普通标点后的连续输入。
- 含待办列表的富文本表格单元格现在可安全接收源码中的待办文字修改和勾选状态切换，并保留原有列表结构。若修改无法安全映射回富文本，例如改变表格形状，编辑器撤回该次修改并给出说明；用户可在富文本视图中修改结构。其他富文本专有结构仍须按上述样本逐项验证，不能仅凭该案例宣称 D 全面通过。
- Windows 10 / Chrome 154 的真实复验和全部样本的保存后重开尚未完成。真实旧版本跨版本验证也尚未完成；如引入存储或跨版本读取变更，须以此作为发布门禁。现有证据不足以宣称 Issue #469 已满足完整无损验收。
